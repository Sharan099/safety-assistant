# ADR-0005: Two small, documented deviations from BACKEND_SCHEMA.md's literal text

- **Status:** Accepted
- **Date:** 2026-08-12

## Context

Implementing `packages/domain` as SQLAlchemy 2.0 models + an Alembic
autogenerate migration surfaced two points where the schema doc as written
needs a small implementation decision.

## Decision 1 — `artifacts.simulation_run_id` FK is deferred (`use_alter`)

`BACKEND_SCHEMA.md` §13/§14 defines a genuine cycle: `artifacts.simulation_run_id
-> simulation_runs`, `simulation_runs.model_version_id -> model_versions`,
`model_versions.source_artifact_id -> artifacts`. Postgres can't create three
tables with a hard cycle between them. Both cycle-forming FKs are nullable by
design (a run's artifact isn't always known yet, an artifact isn't always
tied to a run), so the fix is only about *creation order*, not data model
correctness: `Artifact.simulation_run_id` is declared with
`ForeignKey(..., use_alter=True)`, which makes Alembic emit it as a
post-creation `ALTER TABLE ... ADD CONSTRAINT` instead of an inline
constraint. No column, nullability, or semantics changed.

## Decision 2 — `ArtifactHash` is not a separate table

`BACKEND_SCHEMA.md` §5 lists `ArtifactHash` under Provenance Entities but
gives it no column definition anywhere in the document — every other
provenance entity has one. `Artifact.sha256` (§14) already covers "the
current hash of an artifact," which is everything the doc's usage implies.
Adding a table with no defined shape would mean inventing fields the schema
doc never specified.

**Decision:** do not create `ArtifactHash` in V1. If a real need for hash
*history* emerges (e.g. a re-processed artifact whose hash changes and the
old hash must remain queryable), add it then, with a concrete column list
driven by that need, and update `BACKEND_SCHEMA.md` accordingly rather than
guessing now.

## Consequences

- The autogenerated migration (`packages/domain/migrations/versions/`) matches
  `Base.metadata` exactly; both decisions are visible in `packages/domain/core.py`
  and `packages/domain/provenance.py` as inline comments pointing here.
- If this ADR's guess about `ArtifactHash` turns out wrong, it's a pure
  additive migration later, not a breaking one.

## Correction — 2026-08-13

Decision 1's claim was half wrong: `use_alter=True` does stop SQLAlchemy's
DDL compiler from embedding the FK inline in `CREATE TABLE artifacts (...)`
(true, and why the original migration didn't hit the circular-dependency
error) — but it does **not** make Alembic automatically emit the follow-up
`ALTER TABLE ... ADD CONSTRAINT` anywhere. The original autogenerated
migration never scheduled that ALTER at all, so `fk_artifacts_simulation_run_id`
silently didn't exist in the database from Phase 6 through Phase 8 — no
migration ever failed, `alembic upgrade head` reported success throughout,
and every test that touched `Artifact.simulation_run_id` happened to only
ever insert *valid* references, so nothing exercised the missing
constraint. Caught by coincidence: a routine `alembic revision --autogenerate`
for an unrelated feature (Copilot conversation tables, ADR-0010) diffed live
DB reflection against model metadata and correctly flagged the constraint
as missing. Fixed by applying that migration, which adds it via
`op.create_foreign_key(..., use_alter=True)`, and verified with
`pg_get_constraintdef` before/after plus a check that a subsequent
autogenerate run produces no further diff for it.

**Lesson**: a green migration + passing tests is not proof a constraint is
actually enforced — only checking `pg_constraint` (or trying to insert data
that should violate it) proves that. Worth remembering the next time a
`use_alter` FK gets added anywhere in this schema.
